# DeltaLine Irrigation CRM — Architecture

The CRM is the operating system for an irrigation contractor: lead → customer → property →
irrigation system → estimate → approval/deposit → job → technician → materials/time → signature →
invoice → payment → profit → warranty → maintenance reminder. It sits on top of the existing
**Design Studio** (engineering design: layout, hydraulics, takeoff, plan sets), which provides the
engineering plans that CRM properties link to.

```
Next.js 15 (App Router) · React 19 · TypeScript · Tailwind CSS 4 · zustand
PostgreSQL / Supabase (schema in supabase/migrations) · IndexedDB offline/local mode
```

---

## 1. Database architecture

Two migrations define the production database (validated against Postgres with
`npm run test:sql`, which applies them to an in-memory PGlite instance and smoke-tests triggers,
views and search):

| File | Contents |
|---|---|
| `supabase/migrations/0001_core_schema.sql` | 53 tables, foreign keys, check-constraint enums, indexes, generated columns, `updated_at` triggers |
| `supabase/migrations/0002_security_views.sql` | Row-level security (org isolation + role rules), numbering sequences, derived views, `global_search()`, inventory & payment triggers, Storage bucket policies |

### Entity map

```
organizations ─┬─ users (auth.users ↔ org, role, employee, portal customer)
               ├─ employees ── trucks ── truck_inventory ── inventory_items (price book) ── vendors
               ├─ marketing_sources (campaigns)
               ├─ customers ── properties ── irrigation_systems ─┬─ controllers
               │                    │                             ├─ zones
               │                    │                             └─ components ─┬─ valves
               │                    │                                            └─ sprinklers
               │                    ├─ audit_reports (zone_findings jsonb)
               │                    ├─ warranties (generated labor/mfr expiry)
               │                    └─ service_plan_subscriptions ── service_plans
               ├─ leads ──────────── estimates ─┬─ estimate_options ── estimate_items
               │                                 └─ install_projects (design jsonb, takeoff jsonb)
               ├─ jobs ─┬─ job_items · job_checklist_items · job_costs · job_crew · job_zones
               │        ├─ change_orders
               │        └─ time_entries
               ├─ appointments ── appointment_employees
               ├─ invoices ── invoice_items ── payments
               ├─ inventory_transactions (trigger applies stock movements)
               ├─ photos · documents (polymorphic entity_type/entity_id + denormalized customer/job)
               ├─ messages · message_templates · automations · automation_runs (unique per rule+record)
               ├─ notifications · activity_logs
               └─ integrations · external_refs · webhook_events (prepared)
```

Design decisions

* **Multi-tenant by `org_id`** on every business table; RLS policy `org_id = current_org()` is
  created for all of them in one loop. Child tables without `org_id` (estimate items, job items…)
  inherit visibility through their parent.
* **Role rules** on top of tenancy: field roles can only update jobs they are assigned to / crew on;
  deleting payments/invoices and editing employees is office-only.
* **Text primary keys** generated by the client (`job_xxx`) so offline-created records keep their ids
  when synced. UUIDs also fit.
* **Soft enums** (`text + CHECK`) — adding a status is a one-line migration, no enum rewrites.
* **Money** `numeric(12,2)`; quantities `numeric(12,3)`.
* **Derived data lives in views**, mirroring the TypeScript calculations in `src/lib/crm/calc.ts`:
  `invoice_balances`, `job_costing`, `lead_source_performance`, `low_stock`.
* **Triggers**: `inventory_transactions` insert → warehouse/truck quantity update;
  `payments` change → invoice `partial`/`paid` status.
* **Search**: `global_search(q)` (pg_trgm similarity) across customers, properties, jobs, estimates,
  invoices, zones, components, controllers, employees and price-book items — e.g.
  `select * from global_search('Rain Bird 5000')` returns every property with that model installed.
* **Storage**: bucket `media`, path `<org_id>/<entity_type>/<entity_id>/<file>`, policies scoped by org.

### TypeScript ↔ SQL mapping

`src/lib/crm/types.ts` is the domain model (camelCase, embedded child arrays). The declarative
`src/lib/crm/rowMapping.ts` maps it to the schema (snake_case, flattened value objects such as
`address`/`backflow`/`discount`/`pricing`, child tables). Round-trips are unit-tested.

## 2. Persistence & runtime

```
UI (components/crm) ──► zustand store (store/crmStore.ts) ──► CrmRepository
                         optimistic updates, workflow actions,     ├─ LocalCrmRepository   (IndexedDB, default)
                         activity log, notifications, automations  └─ SupabaseCrmRepository (PostgREST + Storage)
```

* `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` switch to Supabase (see `.env.example`).
* Mutations update memory first (instant UI), then persist; local writes are coalesced (250 ms) so
  typing and dragging cost one IndexedDB write.
* Authentication (`src/lib/crm/auth.ts`): Supabase email/password via GoTrue with org/role/employee
  from `users`; in local mode the "signed-in user" is an employee chosen in the account menu
  (**View as…**) to preview role permissions and the technician app.
* First run seeds a realistic year of history (`src/lib/crm/seed.ts`: ~400 customers, 675 jobs,
  650 invoices, time entries, inventory movements, campaigns, plans, audits, warranties, photos) and
  links the four Design Studio demo projects to their CRM properties (`designBridge.ts`), importing
  their heads/valves/pipes/areas onto the system maps.

### Business logic (pure, unit-tested — `src/lib/__tests__/crm.test.ts`)

| Module | Responsibility |
|---|---|
| `calc.ts` | Pricing rules (multiplier, markup, margin, flat), line totals, estimate option totals (discount, fees, tax on taxable share, margin, markup, deposit), invoice balances & derived status, burdened labor, **job costing** (estimated vs actual + variance reasons), **audit scoring** (overall / efficiency / grade / repairs / upgrades / water savings), warranty expiry |
| `workflows.ts` | Price-book lines, templates → options, estimate → job, job → invoice, deposit invoices, install **material takeoff** generator, schematic system map |
| `metrics.ts` | Revenue/collections series, jobs, conversion, revenue by type/tech, lead-source & campaign ROI, owner financials, cost series, profit by job type |
| `recommendations.ts` | Smart suggestions (repeat repairs → rebuild, old controllers → smart upgrade, estimates not followed up, material/labor overruns, schedule gaps, late techs, unscheduled urgent/approved work, overdue invoices, maintenance due, high pressure) |
| `automations.ts` | Rule engine (estimate follow-ups, invoice on completion, invoice reminders, review requests, audit/backflow/maintenance reminders, purchase alerts, appointment reminders); fires once per record via `automation_runs` |
| `search.ts` | Instant client-side global search (AND-token, ranked) |
| `integrations.ts` | Provider seams + local simulators |

## 4. Key workflows

### Dashboard
KPI row (revenue week/month/year, payments, outstanding/overdue, average ticket, close rate, new
leads) · today's jobs with late detection · "Needs attention" queue (new leads, unscheduled jobs,
estimates awaiting approval, approved-not-scheduled, outstanding invoices, open callbacks,
maintenance due, low inventory) · smart suggestions · charts (revenue over time, jobs completed,
lead conversion & estimate approval, average job value, revenue by service type and technician,
expenses vs revenue) · profit by job (estimated → actual margin) · lead-source performance ·
employee productivity · upcoming jobs · maintenance due · low inventory · recent activity.

### Customer & property
Customers own many properties; each property has one irrigation system (controller + zones +
map components). Profiles compute lifetime revenue, outstanding balance, last service and the next
recommended service. Properties track access (gate code, pets), water supply (meter, static/dynamic
PSI, GPM, line sizes), backflow (type, serial, last test), controller and valve locations, system
age and recommended upgrades.

### Estimate workflow
Template (11 irrigation templates) → options (Good / Better / Best) → line items from the price book
(cost + rule-based price) → live totals: materials, labor, equipment, fees, discount, trip/diagnostic,
tax on taxable lines, total, **gross profit, margin %, markup %, deposit** → send (email template +
portal link; follow-up automations at 2 and 5 days) → customer views/approves in the portal with
option choice and e-signature (or in office) → approval creates the **job** and the **deposit
invoice**, moves the lead to Approved and the install project forward. PDF via print.

### Job workflow
`Unscheduled → Scheduled → En Route → Arrived → In Progress → (Paused / Waiting on Parts) →
Completed → Needs Follow-Up / Callback`. Status changes drive **time tracking** (travel / job timers
per crew member, auto clock-in) and customer messages ("on my way"). The job holds scope,
materials (planned vs **used** quantities), equipment, checklist (per job type), before/during/after
photos with annotations, change orders with digital approval, notes, signature and zones worked on.
Completing a job deducts used materials from the tech's truck (else warehouse), starts warranties,
stamps zone repair dates, rolls service-plan visits and generates the invoice (crediting deposits and
including approved change orders). **Job costing** compares estimated vs actual (materials, labor at
burdened wage, equipment, subs, other) with the reasons for the variance.

### Irrigation system mapping workflow
Property → System map: upload a satellite image / plan / drawing (opacity control) or generate a
schematic from the zone records, or import an engineering plan from the Design Studio. Place heads
(rotor, spray, MP rotator, bubbler, drip), valves, valve boxes, controllers, backflow, meters,
shutoffs, trees, notes; draw main lines, laterals, drip lines, sleeves and wire with distinct colors
and dash patterns; draw lawn, bed, structure and hardscape areas. Select/drag, duplicate, delete,
measure in feet, filter by zone, color by zone / type / condition, toggle layers. Clicking a
component shows type, size, manufacturer/model, zone, install date, condition, notes, photos and
repair history. Print / save as PDF with a title block and zone schedule. Read-only in the
technician app and customer portal.

### New install workflow
Lead → site visit → measure → flow test → pressure test → system design → estimate → approval →
permit → material order → installation → pressure test → coverage test → controller programming →
walkthrough → final payment → warranty. Design data (available GPM, static/dynamic PSI, meter,
service/main/lateral sizes, valve size, controller stations, per-zone heads/flow/PSI/lateral length)
feeds the **material takeoff** generator (or import from the Design Studio analysis) which becomes
the estimate.

### Audits
Static/dynamic PSI, flow, precipitation rate, distribution uniformity, spacing, nozzle match,
broken/low/tilted heads, leaks, overspray, runoff, valve/pressure issues, controller settings,
schedule, soil, sun, slope, plant type and per-zone findings → overall and water-efficiency scores,
grade, prioritized repair and upgrade recommendations, estimated water savings → estimate from
findings · professional PDF report.

## 5. Integrations (prepared)

Every external service is behind an interface in `src/lib/crm/integrations.ts`
(`MessagingProvider`, `PaymentProvider`, `CalendarProvider`, `RoutingProvider`, `AccountingProvider`,
`WebhookProvider`, `WeatherProvider`) with local simulators so all workflows run today. Production
providers run as **Supabase Edge Functions** holding secrets in Vault (never in the browser) and are
registered with `registerProvider()`. Tables `integrations`, `external_refs` (QuickBooks / Stripe /
Google ids) and `webhook_events` (idempotent inbound events) are in the schema. Targets: Google
Calendar, Google Maps (geocoding, drive-time routing), QuickBooks, Stripe, Square, Twilio, Gmail,
Google Drive, Zapier, weather, manufacturer catalogs. The automation engine is pure, so the same
code runs on a server cron.

## 6. UI system

* Token-based theming: semantic colors (`surface`, `canvas`, `ink`) and a validated categorical
  chart palette (`--color-s1…s8`); dark mode re-steps the neutral scale and tints so every screen,
  including the Design Studio, follows the theme; applied before paint.
* Components: `components/crm/ui.tsx` (cards, tabs, segmented controls, badges, slide-overs, menus,
  KV lists, stat tiles), `DataTable` (sort, incremental rendering, phone card layout, CSV export),
  `charts.tsx` (SVG line/area with crosshair tooltip, bars, ranked bars, sparklines — one axis,
  legends for ≥2 series), pickers (searchable combobox), line-item editor, signature pad,
  photo annotation, printable documents.
* Desktop: dense tables, sticky headers, slide-over panels. Phone: card lists, bottom navigation in
  the technician app, ≥44 px touch targets.
